sdlc-kit

Four phases for AI that builds software: understand first, prove last.

AI tools that write software are fast, and being wrong is still expensive. They guess what you meant and grade their own work. With sdlc-kit the AI confirms what you asked, explores before it changes anything, has its work checked by separate AIs, and lets a score decide whether it is done.

Four phases, with checkpoints between them

Each phase writes down what it found or did, and the next one starts only when its checkpoint opens. By default a person confirms the request. A plan with a risk flag also waits for a person, and you can choose to approve every plan yourself.

  1. 1 · Intent what you asked

    The AI writes down what you asked, what it understood, and the risks in that understanding. It asks only the questions whose answers would change what gets built.

  2. checkpoint · a person confirms

  3. 2 · Plan one plan page

    Several helper AIs explore at the same time: the rules that decide the behaviour, the data, the logic, and how users reach it today. Each writes notes. One plan page holds before and after, side effects, and the scenarios that will be tested. A separate AI checks it for gaps.

  4. risk flag · a person approves

  5. 3 · Build the smallest complete change

    The AI makes the smallest change that fully does what the plan says. A separate AI then reviews it, assuming it is wrong. After three failed reviews the work stops for a person.

  6. review passes · goes on

  7. 4 · Evidence scored proof

    The project's real checks run first. Then every scenario is played as its user, through the same screens and commands that user really works with. A script scores the result, so the AI cannot grade its own work.

The rules are checked in this order. Each kind of return happens at most three times, then a person decides. A scenario that could not run counts as failed, and only a person can remove a scenario.

What you get

The AI follows the same written rules in every phase. Here is what they give you.

You confirm what matters
The AI records your approval only after you say so plainly. Silence, "continue" or its own judgement do not count. If an approved page is edited later, its checkpoint and every one after it close again.
Side effects found before any change
The helpers look at everything else that reads or writes the same data before anything is changed, and each side effect gets a scenario that checks it. Facts that earlier work verified are kept, and the next job reads them first.
Separate AIs check the work
The helpers who explore, the reviewer and the tester each start fresh. None of them is the AI that wrote what it checks, and none of them changes it. If no separate helper is available, that gap is written down.
Proof behind every "passed"
Every pass points to the record of what was run or seen. If there is nowhere to try something, it is marked as blocked, never as passed. A bug fix needs a test that failed before the fix and passes after it. The list of scenarios becomes your own checklist.
Delivered means what was verified
Closing a job is refused if what was delivered differs from the version that was checked. Risky work always needs your word first, under every setting: deleting data, reshaping stored data, changing what other systems rely on, security, infrastructure, and sending the work beyond this computer. What the AI reads along the way counts as information; it takes instructions only from you.

What it cannot do

The kit records and counts; it never runs an AI itself, so the work is only as careful as the AI tool you use. It saves the words of each approval but cannot prove who said them. A scenario with nowhere to run cannot pass, so some work stops and waits for you. The records stay on the computer where the work runs and are not saved with the project, so back them up.

For the person who sets it up

This part uses commands. Three steps set it up in a project, and the README on GitHub has the details. After that, ask for a change in plain words.

  1. git clone https://github.com/cskwork/sdlc-kit ~/sdlc-kit ln -s ~/sdlc-kit ~/.claude/skills/sdlc-kit

    Once per computer. The link is for Claude Code; use your tool's skills folder. Without one, add For SDLC work, read ~/sdlc-kit/SKILL.md and follow it. to AGENTS.md, CLAUDE.md or GEMINI.md.

  2. cd /path/to/your-project ~/sdlc-kit/sdlc.sh init

    Once per project, or per shipping unit of a monorepo. Creates .sdlc/, which git ignores. On Windows, run sdlc.sh in Git Bash or WSL.

  3. $EDITOR .sdlc/config.md

    The only project-specific file: the build, test, lint, run and e2e commands, the qa tool, human_gates (default intent; add plan to approve every plan) and the knowledge folder.
